probe 慢，先怀疑 regulator 的上电时序，最后才怀疑内核。

2026/11/21

顺序是：量 regulator enable 到输出稳定的时间 → 看 driver 的 probe 里有没有 I2C 轮询等待 → 查有没有 -EPROBE_DEFER 反复重试 → 才轮到调度和 CPU 频率。
大多数「内核慢」最后都是硬件时序。

看到 -517 就是 EPROBE_DEFER，不是失败。

2026/11/20

-517 的意思是「我依赖的东西还没准备好」，内核让你等一等。真正要查的是那个依赖为什么没起来 —— 常见是 regulator、clk、gpio 的驱动还没 probe 完。

dmesg 里 Freeing unused kernel memory 是内核态和用户态的分界线。

2026/11/19

它之前全是内核初始化，之后才是 init。算启动耗时必须先按这一刀切开，否则会把用户态的慢算到内核头上。

两份 dts 用了同一个 GPIO，编译一声不响，上板才发现。

2026/11/18

pinctrl 里 A 节点用了 GPIO3_A2，B 节点也用了。合并时不会报冲突，因为语法完全合法。只有运行时读 pinmux 寄存器才知道谁赢了。
多人并行改 dts 时这是高频事故。

initcall_debug 只能启动前打开，别人的 log 事后用不上。

2026/11/16

所以拿到一份现成的 dmesg，只能靠时间戳差值人工找嫌疑：

[    0.823] probe of 1c28000.i2c returned 0 after 1204 usecs
[    1.457] probe of fe2b0000.ethernet returned -517 after 3 usecs

这两行差了 0.6 秒，真正的嫌疑是第一行 —— 它自己花了 1.2ms。

I2C 通信失败，先量上拉电阻，再看时序。

2026/11/15

4.7k 上拉在 400k 速率下边沿常常太慢。示波器看 SCL 上升沿，如果爬到 3.3V 用了几百纳秒，就是它。

# 先确认设备在不在总线上
i2cdetect -y 1
# 再读一遍寄存器，看有没有响应
i2cget -y 1 0x38 0x00

曾经因为这个换过一整批板子上的电阻。

设备树 reg 区间重叠，编译器不报，运行时内存被踩。

2026/11/13

两个节点都从 0x10000000 起、长度各 0x1000 —— 完全合法。这类问题只能自己写脚本扫，靠 review 看是看不出来的。

间隔重复的关键不是复习，是在「快忘记」的那一刻复习。

2026/11/11

太早复习是浪费，太晚复习等于重学。所以真正要算的不是「第几天复习」，是「你有多大概率还记得」。
难度系数 ease 就是这个估计。

本地优先不是「离线能用」，是「本地数据才是唯一真相」。
